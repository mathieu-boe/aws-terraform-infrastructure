# AWS Terraform Infrastructure

An infrastructure-as-code project built as part of my hands-on AWS and DevOps portfolio. This project extends the [Containerised Operations API](https://github.com/mathieu-boe/containerised-operations-api) by developing the AWS infrastructure required to host, secure, and monitor the application using Terraform.

## Objectives

- Provision and manage AWS infrastructure using Terraform.
- Apply least-privilege IAM permissions and secure network configuration.
- Build a VPC and supporting networking resources for the application.
- Deploy the Containerised Operations API to an EC2 instance using Docker.
- Use Amazon S3 for operational report storage.
- Configure CloudWatch monitoring, logs, metrics, and alarms.
- Automate Terraform formatting and validation using GitHub Actions.
- Practise infrastructure planning, change review, deployment, and resource cleanup.
- Document security considerations, deployment procedures, and AWS cost management.

#### Operational reports storage

The intended use case is a private S3 bucket for operational reports generated by the [Infrastructure Automation Toolkit](https://github.com/mathieu-boe/python-infrastructure-toolkit).

The Terraform configuration selects the S3 account-regional namespace, blocks public access, enables SSE-S3 encryption, and enables versioning. The bucket name is derived from the AWS account ID and deployment Region.

These settings are currently defined in Terraform; the bucket has not been deployed. Versioning can retain previous object versions and increase storage usage. Retention, cleanup, and any required access permissions must be reviewed before deployment.

## Development

Terraform defines the AWS infrastructure as code. The planned environment includes IAM, VPC networking, EC2, S3, and CloudWatch. Docker will be used to run the Containerised Operations API during the application deployment phase.

Configuration is developed and validated locally before AWS resources are provisioned. AWS authentication uses a locally configured authentication mechanism; credentials and secrets must never be committed to version control.

### Repository structure

```text
.
├── .github/
│   └── workflows/
│       └── terraform.yml
├── .gitignore
├── .terraform.lock.hcl
├── README.md
├── compute.tf
├── iam.tf
├── networking.tf
├── outputs.tf
├── providers.tf
├── security.tf
├── storage.tf
├── variables.tf
└── versions.tf
```

Terraform working directories, local virtual environments, saved plans, and state files are excluded from version control as appropriate. The provider lock file is committed to help keep provider selections consistent.

### Prerequisites

- Linux or WSL2 with Ubuntu.
- Git.
- Terraform CLI compatible with the constraints in `versions.tf`.
- AWS CLI and an appropriately authenticated AWS identity for AWS operations.
- An AWS account for deployment and AWS-side validation.
- Docker for the application containerisation phase.

### Terraform configuration

The project defines Terraform and AWS provider version requirements in `versions.tf`. The AWS provider configuration in `providers.tf` uses variables to select the deployment Region and environment.

The default deployment Region is `eu-west-2` (London), and the default environment is `dev`.

### Initialise Terraform

Run from the repository root:

```bash
terraform init
```

Initialisation downloads the required provider plugins and prepares the working directory. It does not provision AWS infrastructure.

To initialise without configuring a backend:

```bash
terraform init -backend=false
```

### Format and validate the configuration

Check formatting:

```bash
terraform fmt -check -recursive
```

Apply canonical formatting when necessary:

```bash
terraform fmt -recursive
```

Validate the configuration:

```bash
terraform validate
```

Validation checks Terraform configuration structure and consistency. It does not prove that AWS permissions are sufficient, that every service setting will be accepted during deployment, or that the infrastructure will work as intended.

### Review infrastructure changes

Once AWS authentication is configured and the desired infrastructure has been implemented, generate a plan:

```bash
terraform plan
```

Review the proposed changes, resource dependencies, permissions, network exposure, and expected costs before applying them. Do not apply infrastructure until the plan has been reviewed and deployment is explicitly intended.

### Continuous integration

The GitHub Actions workflow in `.github/workflows/terraform.yml` runs on pushes and pull requests targeting `main`. It checks Terraform formatting, initialises Terraform without configuring a backend, and validates the configuration.

The workflow does not deploy infrastructure to AWS.

## Security and cost

- Never commit AWS credentials, access keys, secrets, Terraform state, or sensitive variable files.
- Prefer temporary credentials and IAM roles over long-lived access keys.
- Apply least-privilege IAM policies and restrict inbound network access.
- Keep S3 buckets private and enable appropriate encryption and access controls.
- Review Terraform plans before applying changes.
- Protect Terraform state if a remote backend is introduced.
- Monitor AWS spending and use cost controls appropriate to the account.
- Remove resources when they are no longer required, after reviewing dependencies and cleanup requirements.
- Remember that EC2 instances, storage, networking, logs, and monitoring resources may incur charges.
- Review S3 version retention and cleanup requirements to avoid unnecessary storage growth.

This is a learning project. Production deployment would require additional security controls, availability planning, monitoring, operational procedures, and a reviewed infrastructure lifecycle.
